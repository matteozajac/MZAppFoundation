# MZAppFoundation setup

Locate the MZAppFoundation checkout separately from the target app. For a repository-backed installation, resolve the skill directory's symlink and check its `../..` for `scripts/setup.py`, `Package.swift`, and `docs/integration.md`. A copied skill may need a separate matching checkout; do not assume the app contains foundation scripts or documentation. Repository-relative links below refer to that foundation checkout.

Read [integration](../../docs/integration.md) before wiring an app, [provisioning](references/provisioning.md) only for requested provider work, and [migration](../../docs/migration.md) when adopting an existing app. Check `VERSION`, the manifest and resolved app dependencies before selecting APIs. The dependency-free core uses Swift tools 6.2; use Swift 6.2.3+ for the root vendor composition, iOS/visionOS 26 and macOS 15 minimums; do not silently raise an existing app's deployment target.

## Outcome

App feature code imports `MZAppFoundation`, with injected package-owned interfaces. Bootstrap, app entrypoint, and developer settings import composition/UI modules. Local app targets link the Pulse composition; modern device targets select independent adapters only for supplied providers. Compatibility Live/Firebase products remain available for existing imports and older pinned versions. Standalone core/UI use `Packages/Core`, with no external dependencies.

## Workflow

1. Inspect the app's instructions, Git state, project file, target/deployment settings, existing SDK imports and initialization, event schemas, purchase definitions, and provider identities. Do not infer that a similarly named remote project belongs to this app. Preserve app-specific policies and unrelated changes.
2. Create `.mzappfoundation/config.json` using `../../docs/config.example.json`. Existing apps keep their own analytics/diagnostics defaults. The example disables both remote delivery preferences; choose explicit defaults and independent controls matching the new app's policy. Omitting those fields uses the generator's enabled defaults. Fill schema entries from real app event definitions; empty schema means no product events are delivered.
3. Set `FOUNDATION_ROOT` to the located foundation checkout and `APP_ROOT` to the target app checkout. Activate a virtual environment with dependencies from the foundation's `scripts/requirements.txt`. Run `python3 "$FOUNDATION_ROOT/scripts/setup.py" inspect --app-root "$APP_ROOT"`. All three setup modes require `--app-root`; use `--config /path/to/config.json` only for a non-default manifest. For requested providers, resolve catalog/resource matches using the provisioning reference and the app owner's connected tools or CLI. No authenticated connection, account, organization or project is bundled with this skill. Preserve an intentionally local-only composition when providers are outside scope.
4. Run `python3 "$FOUNDATION_ROOT/scripts/setup.py" apply --app-root "$APP_ROOT"`. XcodeGen requires `xcodegen`; native Xcode requires the Ruby gems in the foundation's `scripts/Gemfile` (use `RUBY` to select a compatible interpreter). Review the generated project changes. For inherited XcodeGen target templates, xcconfigs, extensions, or custom build phases, inspect effective settings; the script cannot safely infer every transitive dependency.
5. Integrate `MZBootstrap.services` and developer tools into the existing app entrypoint. For iOS with `bug_reporting: true`, use `.appDeveloperTools(services.developerOptions, reporting: MZBootstrap.reporting)` and add `DeveloperReportingSettings(reporting:)` or its composed foundation page to developer Settings. Setup preserves or supplies `NSMicrophoneUsageDescription`; verify the built app contains it. For console-only apps, keep `.appDeveloperTools(services.developerOptions)`. On visionOS/macOS register `DeveloperConsoleScene`; modern foundation settings also require `FoundationSettingsScene` for automatic window presentation. Read [reporting integration](../../docs/bug-reporting.md) and [developer settings](../../docs/developer-settings.md). Preserve unrelated deep links, delegates, scenes, and startup behavior. Move vendor-dependent app adapters out of local target membership; replace feature call sites with injected interfaces. App-specific paywall UI and access policy remain app-owned.
6. Run `python3 "$FOUNDATION_ROOT/scripts/setup.py" verify --app-root "$APP_ROOT"`. It checks generated source and selected wiring; it does not compile, exercise the UI, or prove binary isolation. Build applicable local targets and selected device adapters. For an iOS/visionOS local bundle, run `python3 "$FOUNDATION_ROOT/scripts/audit_binary.py" /path/to/MyAppLocal.app --local`. This helper expects `Info.plist` and the executable at the bundle root and checks main-executable/debug-library symbols and bundle filenames. For macOS inspect `Contents/Info.plist`, `Contents/MacOS` and embedded frameworks separately; the helper does not support that layout. Inspect embedded targets/frameworks and build logs as appropriate. Run core tests and relevant app behavior tests. Check console/shake and Command–D where supported, restoration of existing iOS sheets/alerts after console dismissal, keyboard help with developer mode off, injected feature shortcuts, platform settings presentation, enable/disable and dry-run links, expiry/dismissal, and independent telemetry preferences. Exercise missing-provider and purchase recovery paths when configured. Manual provider actions must follow the app's runtime/delivery policy; submitted events still need dashboard readback. For iOS reporting, check the Ladybug action, recording/permission/cancellation, title-or-audio sharing and diagnostics selection, then inspect an exported ZIP with [app-bug-report](../app-bug-report/SKILL.md). Record device/provider checks as unverified when the necessary device, account or runtime is unavailable.
7. Run apply again and ensure no unintended diff. Record implemented, configured, built, simulator-verified, device-verified, and provider-verified status separately. Missing credentials, absent products, or unperformed device checks are explicit partial states. Commit/push only the requested repository work.

## Developer settings and evidence

Follow [developer settings](../../docs/developer-settings.md). Independent adapters and protected settings were introduced in 0.5.0; setup now defaults to 0.6.2 with keyboard help, Command–D, console presentation above existing iOS sheets/alerts, and short app-specific links. Use `package_path` for local development. Explicitly pinned older integrations retain compatible generation; do not insert newer APIs until upgraded. Setup itself does not publish packages/apps or migrate other repositories.

- Add `FoundationSettingsLink(services:pages:)` to settings. Automatic presentation uses an iOS sheet and macOS/visionOS sidebar window; register `FoundationSettingsScene` on the latter or explicitly choose `.sheet`. On macOS add `FoundationSettingsCommands` for Command–D console, its Option–Command–L alias, and Control–Option–Command–D settings. Pass consistent pages to the link and scene. Every developer destination is gated, and disabling/expiry dismisses it. Current developer copy remains English; do not perform localization unless separately requested.
- Add `FoundationKeyboardShortcutsLink(options:sections:)` to ordinary settings so help stays available with developer mode off. Inject feature descriptions with `FoundationKeyboardShortcutSection` and bind actions using the same `FoundationKeyboardShortcut.shortcut`; a help entry alone does not install an action. Pass the same sections through `keyboardShortcutSections:` to the settings link/view/scene. The settings scene registers the help window on macOS/visionOS; use `FoundationKeyboardShortcutsScene` independently or choose help `presentation: .sheet` when appropriate. Keep developer rows and their gating in the package.
- Use `FoundationDiagnostics` ordered `ProviderRequirement` rules for required/optional/intentionally unused providers per environment/platform; the last matching rule wins. Declare intended identities separately from supplied labels. Preserve unknown running identity where public SDKs cannot establish it. A global enabled flag is not initialization ownership. The overview issues filter follows warning/error findings.
- Modern setup chooses `MZAppFoundationRevenueCat`, `MZAppFoundationSentry`, and iOS `MZAppFoundationFirebaseAnalytics` independently. Inject owned adapters through `LocalServices.make` purchase/additional-analytics/additional-diagnostics parameters and corresponding passive diagnostic builders. Use unavailable purchases when no real provider exists; mocks remain deliberate local QA. Preserve existing umbrella APIs where migration is not requested.
- `VERSION` and the generator supply compiled foundation version/package metadata. Setup adds a build phase writing `MZFoundationBuildMetadata.plist` with app/foundation revisions, dirty flags, channel/date and resolved versions. Leave unstamped facts unknown and distinguish runtime SDK versions from lockfile metadata. Startup records must preserve the failed provider/stage, correction and partial recovery without serializing arbitrary vendor errors.
- Counters count calls and per-adapter outcomes; overlapping reasons/multiple adapters do not sum into a single call partition. The process-local timeline is bounded and contains only typed events, never payloads. Passive inspection/export must not initialize providers or issue requests. Manual Firebase/Sentry checks return submitted correlation references and need dashboard confirmation; RevenueCat refresh follows ordinary entitlement verification and records per-entitlement environment/freshness rather than assigning one customer environment.
- `services.diagnosticExport()` produces versioned, redacted JSON/text. Opt into an iOS `diagnostics.json` report attachment with one `DeveloperReporting(services:)` instance or its capture closure; inclusion defaults on when supplied and the report form permits exclusion. Keep report data local until deliberate sharing. Use typed `FoundationDiagnosticInspection` / `FoundationDiagnosticSection` for app services, with exportable field IDs explicitly selected; use `FoundationDeveloperPage` for app-owned tools. Never place credentials/user content in these surfaces.
- Use the app's unique `url_scheme` for `<app-scheme>://developer/enable` and `/disable`; do not add the bundle ID or an app host. Generate with `DeveloperDeepLink.url(for:scheme:)`. For 0.5.1/current local setup, remove old shared-scheme registration and reject shared or long host-based developer routes. Apple documents undefined target-app selection when multiple apps register the same scheme. [Apple custom-scheme routing](https://developer.apple.com/documentation/xcode/defining-a-custom-url-scheme-for-your-app)
- Keep the shared `DeveloperOptions.preferenceKey` spelling while values remain defaults-store scoped. Migrate older keys explicitly. Link inspection and QR sharing do not execute links. Timed/session access stores false for the next launch; saved access persists.
- Local QA scenarios are a separate mock composition for missing configuration, offline, pending purchase and failed verification. They require a local debug/simulator/test/preview runtime, never replace live services, and cannot grant real purchase authorization. Do not infer package debug flags from app flags.

## Diagnostic logging

Use [app-logging](../app-logging/SKILL.md) when wiring or migrating logs. MZAppFoundation 0.2.0 adds error-taking `AppLogging.error` calls, `ErrorSnapshot`, source locations, and shared Pulse/Sentry routing. Pass the actual Error whenever available; keep metadata out of messages and forward caller location through wrappers. Capture snapshots before asynchronous delivery. Reporting stacks are not original throw stacks. Inspect error details in PulseUI on iOS/visionOS; macOS's native message list omits metadata, so inspect its local store or adapter test output for detailed fields. Existing diagnostic delivery preferences remain authoritative.

## Non-obvious constraints

- Public releases include Pulse, but developer mode defaults off. Local/Debug/Internal defaults on; an explicit persisted enable/disable wins. Deep links never change remote delivery or purchase verification.
- Simulator, preview and unit-test paths cannot initialize live providers. Source `#if` guards do not remove linked SDKs: maintain separate local and device target dependencies.
- `MZ_LOCAL` and `MZ_INTERNAL` belong to the app's build settings. Do not assume app compilation flags propagate to Swift packages.
- Firebase covers bootstrap/Analytics only. Preserve app-owned Auth/Firestore/Functions/etc. The Analytics adapter is iOS-only; macOS/visionOS may still inspect configuration and display provider state without that SDK.
- Only declared event/property schema crosses analytics engines. Never put user-authored text, tokens, identifiers, receipts, or raw error descriptions into log messages or diagnostic codes. Local Pulse is not an exemption.
- Instrument network calls explicitly through `InstrumentedSession`; no global proxy. Bodies and query values are omitted. Apps must omit sensitive URL path segments or exclude those calls from instrumentation.
- Administrative keys belong in environment/secure CI storage. RevenueCat public Apple SDK keys, Sentry DSNs, and Firebase app configuration are client configuration, not administrative tokens. Never echo private credentials.
- RevenueCat app registration is allowed without products. Create offerings/packages/entitlements only from confirmed existing app product definitions. Do not invent prices, create store products, or grant real access from mock state.
- Do not bootstrap duplicate Firebase/Sentry/RevenueCat owners. Bootstrap conflicts require reconciliation, not another singleton.
- A successful build does not prove crash delivery, Sentry symbol readback, Firebase collection, or purchase/restore on a physical device.

Bug reporting in 0.3.0 is iOS-only and explicitly enabled in setup configuration. QA notes, audio, screenshots and video remain local report attachments; never send them through logging, analytics or Sentry. Existing apps retain their deployment target and pinned SDKs until an explicitly scoped migration.
